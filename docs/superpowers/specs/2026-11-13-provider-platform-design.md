# Платформа провайдеров — дизайн

Дата: 2026-11-13. Статус: на согласовании.
Часть плана первого открытого релиза eagle (0.1, все десктопы). Это первый из пяти проектов: провайдеры → вход/выход → история и плейлисты → волна → интерфейс.

## Зачем

Сейчас eagle — по сути клиент Яндекс Музыки: в `app` одно поле `provider: Arc<dyn Provider>` с жёстко подставленным `eagle_yandex::Yandex::new` (`session.rs`, `downloads.rs`, `playback.rs`, `music.rs`), аккаунт — одна строка `account_uid:yandex`, `store` чистит лайки и плейлисты запросом `LIKE 'yandex:%'`, экран входа написан под Яндекс. Провайдер VK — пустая заготовка.

eagle выходит в открытый доступ. В 0.1 встроен только Яндекс, но код должен стать **площадкой, на которой другие разработчики добавляют своих провайдеров** (VK и любые другие), не трогая ядро. Пользователь при этом видит одну медиатеку: треки из разных сервисов живут в одних плейлистах и очереди, одинаковые треки склеены, при недоступности источник подменяется.

## Цели

1. Отдельный крейт `eagle-provider-sdk` — единственное, от чего зависит провайдер. С ним, шаблоном и тестовым набором сторонний разработчик пишет провайдер, не читая `app`/`store`/`ui`.
2. Провайдер сам сообщает свои **возможности** и **способ входа**; UI и `app` строятся по этим данным, а не по имени провайдера.
3. **Реестр провайдеров** в `app` вместо одного поля; пользователь задаёт **порядок приоритета** провайдеров.
4. **Склейка**: одинаковые треки (и исполнители) у разных провайдеров — одна сущность для пользователя.
5. **Подмена источника**: если трек недоступен у выбранного провайдера, играем его связанную версию у следующего по приоритету.
6. **Возможности с подменой**: функцию, которой нет у одного провайдера, берём у следующего по приоритету, который её умеет.
7. **Лайки — наши**: хранятся локально и отправляются во все подключённые сервисы, где есть связанный трек; лайки провайдеров подтягиваются в нашу медиатеку при синхронизации.
8. **Профиль отдельно от аккаунтов провайдеров**: без входа eagle работает (история, локальные плейлисты, локальные лайки); вход в провайдер добавляет его каталог.
9. Яндекс переезжает на SDK и становится образцом. Поведение для пользователя с одним Яндексом не меняется, кроме исправлений из этого документа.

## Не цели (в этом проекте)

- Провайдер VK — после 0.1, встанет в готовую площадку.
- Загрузка провайдеров во время работы (WASM, dylib, внешние процессы). Провайдеры добавляются в исходный код и собираются вместе с eagle: память и нагрузка критичны.
- Интерфейс входа и выхода (встроенный браузер, «оставить сохранённое?») — проект «вход/выход». Здесь — только модель аккаунтов и команды, на которых он будет стоять.
- Своя волна, локальные плейлисты с «+», дедупликация истории, экран «Все треки», правки интерфейса — следующие проекты. Здесь закладывается только то, без чего они не встанут (группы треков, профиль).
- Ручная склейка/расклейка треков пользователем.
- Несколько аккаунтов одного провайдера.
- Полный рефакторинг `session.rs`.

## Анти-цели (провал, даже если работает)

- Провайдер тянет зависимости на `app`, `store`, `ui`, `engine` или знает про SQLite.
- В `app`/`store`/`ui` остаётся ветвление по имени провайдера (`"yandex"`, `LIKE 'yandex:%'`) вне самого крейта провайдера.
- Регресс памяти или пробуждений в фоне по сравнению с текущей базовой линией (`cargo xtask bench`).
- Склейка путает разные треки или разных исполнителей с одинаковым именем. Лучше не склеить, чем склеить неправильно.
- Пользователь с одним Яндексом теряет лайки, плейлисты, сохранённое, историю или позицию воспроизведения после обновления.

## Ограничения

- Rust 2024, MSRV 1.92, Google Rust Style; ошибки через `thiserror`, логи через `log` с kv; без `unwrap`/`expect` в рабочем коде; без `tracing`; без новых зависимостей без необходимости.
- Сеть блокирующая (`ureq`), без tokio, сетевых воркеров немного. Опрос нескольких провайдеров не должен плодить потоки на каждый запрос.
- Логи на info — только provider/track_id; секреты только в `Token`/`SignedUrl`.
- Права на офлайн (`access`, `offline_owners`, `downloads.account`) привязаны к **аккаунту провайдера**, а не к профилю: сохранённый трек проигрывается локально только для того аккаунта, у которого есть права. Эту логику нельзя ослабить.
- Существующие базы пользователей мигрируются (`PRAGMA user_version`), без потери данных.
- Коммиты в формате `[FEATURE] …`/`[FIX] …`/`[DEV] …`; `cargo fmt --check` и `cargo test` зелёные.

## Подходы (рассмотрены)

1. **Провайдеры в исходном коде + SDK-крейт** — выбран. Ноль накладных расходов, работает на всех платформах, включая iOS. Минус: чтобы добавить провайдер, нужен PR и пересборка.
2. WASM-плагины (WIT) — ставятся без пересборки, песочница, но рантайм ест память, HTTP и потоки приходится гонять через хост; отдельный большой проект. Отклонён.
3. Внешний процесс по протоколу — лишние процессы бьют по памяти и батарее, на iOS невозможен. Отклонён.

Выбран 1, потому что память и нагрузка для eagle критичнее, чем установка провайдеров без пересборки.

Для лайков рассмотрены: (а) локальные лайки, зеркалируемые во все подключённые сервисы — **выбран**; (б) лайк только в провайдер, который сейчас играет, — отклонён: медиатека зависела бы от случайного источника.

## Решения пользователя

- В 0.1 встроен только Яндекс; цель — площадка для других разработчиков.
- Провайдеры — в исходном коде, без рантайм-загрузки.
- Смешанные плейлисты хранятся локально.
- Одинаковые треки у разных провайдеров склеиваются; исполнители — тоже, для всех провайдеров.
- Если трек недоступен у провайдера — ищем связанную версию у другого.
- Источник проигрывания выбирается по приоритету провайдеров.
- Возможности, которых нет у провайдера, остаются в интерфейсе и берутся у другого провайдера по тому же приоритету.
- Вход сейчас по токену, в перспективе — удобнее, возможно через встроенный браузер.
- Один аккаунт на провайдер. Без входа eagle работает.
- Лайки — вариант (а).
- Лайки не теряются при выходе из сервиса и переходе на другой: выход из провайдера лайки не трогает.
- Старые лайки отправляются в позже подключённый сервис только с согласия пользователя.

## Дизайн

### 1. Крейт `eagle-provider-sdk`

Новый крейт `crates/provider-sdk` (имя пакета `eagle-provider-sdk`). Содержит то, что сейчас лежит в `eagle-core` и относится к границе провайдера:

- модели: `TrackId`, `Track`, `Artist`, `Album`, `ArtistPage`, `Playlist`, `PlaylistSnapshot`, `PlaylistEdit`, `PlaylistTrack`, `Page`, `Stream`, `Quality`, `Encryption`, `Availability`, `Account`, `AccessCheck`, радио-типы;
- ошибки: `ProviderError`, `PlaylistEditError`, `RadioError`;
- секреты: `Token`, `SignedUrl`;
- трейт `Provider` (см. ниже);
- `Capabilities`, `ProviderInfo`, `AuthMethod`;
- HTTP-доступ провайдера — через трейт `Http` (или существующий тип из `eagle-net`, если его можно отдать без утечки внутренностей; решает исполнитель), чтобы провайдер не создавал свой клиент и шёл через общие ретраи, лимиты и прокси.

`eagle-core` реэкспортирует SDK (`pub use eagle_provider_sdk::*`), чтобы остальной workspace не пришлось переписывать разом. Новые внутренние типы ядра (группы треков, профиль) живут в `core`, а не в SDK.

Внутри SDK:
- `testkit` (фича `testkit`): набор проверок соответствия, который автор провайдера запускает из своих тестов на записанных ответах (ID корректны и проходят `TrackId::from_str`, заявленные возможности реально не возвращают `Unavailable`, пагинация конечна, `resolve_stream` даёт непустой URL и срок жизни в будущем и т. п.), плюс `FakeProvider` — настраиваемый провайдер в памяти.
- `README.md` в крейте: как написать провайдер, правила (без своих потоков, без логирования секретов, блокирующий API, курсоры непрозрачны), как зарегистрировать.
- Шаблон `crates/providers/_template` (или `cargo generate`-шаблон в `docs/`; решает исполнитель) — минимальный компилирующийся провайдер с тестом через testkit.

### 2. Возможности и описание провайдера

```rust
pub struct ProviderInfo {
    pub id: &'static str,          // "yandex"; совпадает с префиксом TrackId
    pub name: &'static str,        // «Яндекс Музыка»
    pub auth: AuthMethod,
    pub capabilities: Capabilities,
}

pub enum AuthMethod {
    None,                          // каталог без входа
    Token { hint: &'static str, help_url: Option<&'static str> },
    Browser { start_url: String, done: RedirectMatch }, // заложено, UI — в проекте «вход/выход»
}

pub struct Capabilities {
    pub search_tracks: bool,
    pub search_artists: bool,
    pub search_albums: bool,
    pub search_playlists: bool,
    pub likes: bool,
    pub dislikes: bool,
    pub liked_albums: bool,
    pub liked_artists: bool,
    pub playlists_read: bool,
    pub playlists_edit: bool,
    pub artist_page: bool,
    pub artist_all_tracks: bool,   // нужен для экрана «Все треки»
    pub radio: bool,
    pub play_reporting: bool,
    pub offline: bool,
    pub lyrics: bool,
    pub isrc: bool,                // отдаёт ли ISRC в Track
}
```

**Возможности статические и по аккаунту** (решение исполнителя-ревью): `info().capabilities` — что провайдер умеет в принципе; `Account` получает поле `capabilities: Capabilities` — что доступно этому аккаунту (подписка, регион). Действующие возможности = пересечение. Подмена по возможности (§3) и `ProviderStatus` используют действующие. testkit проверяет заявленное на тестовом аккаунте с полными правами.

`Capabilities` — простая структура из `bool` (без новых зависимостей), с `#[non_exhaustive]` и `Default` (всё `false`), чтобы новые поля не ломали существующих провайдеров. SDK живёт только в этом репозитории: провайдеры принимаются через PR, отдельные релизы и semver SDK не нужны. Трейт получает `fn info(&self) -> &ProviderInfo` вместо `fn name()`. Методы с реализацией по умолчанию `Err(Unavailable)` остаются, но `app` больше не вызывает их «на удачу»: сначала смотрит возможности.

Изменения трейта:
- `fn info(&self) -> &ProviderInfo` (заменяет `name`);
- `fn logout(&self)` — забыть токен в памяти провайдера;
- `fn artist_tracks(&self, id, cursor) -> Result<Page<Track>, _>` — все треки исполнителя постранично (по умолчанию `Unavailable`);
- в `Track` — необязательное поле `isrc: Option<String>` (`#[serde(default)]`).

Провайдер **не** хранит токен на диске — это делает `app` через `platform`/`keyring`, ключ по `info().id`.

### 3. Реестр и приоритет

В `app` новый модуль `providers.rs`:

```rust
pub struct Providers {
    all: Vec<Arc<dyn Provider>>,   // порядок = приоритет пользователя
}
impl Providers {
    fn get(&self, provider_id: &str) -> Option<&Arc<dyn Provider>>;
    fn signed_in(&self) -> impl Iterator<Item = &Arc<dyn Provider>>;
    fn with_capability(&self, f: impl Fn(&Capabilities) -> bool) -> impl Iterator<…>; // по приоритету
}
```

- Список встроенных провайдеров — одна функция `builtin(net) -> Vec<Arc<dyn Provider>>` в `app` (сейчас — только Яндекс). Добавить провайдер = добавить крейт в workspace и одну строку сюда.
- Порядок хранится в настройке `provider_order` (список id); новые провайдеры дописываются в конец, неизвестные id игнорируются.
- `Worker.provider` заменяется на `Worker.providers: Arc<Providers>`; `Catalog`, `Downloads`, `playback.rs`, `music.rs` получают реестр. Каждый вызов к провайдеру выбирает его по `TrackId::provider()` объекта или по возможности.
- `Session::start_with_provider` → `start_with_providers(Vec<Arc<dyn Provider>>)` для тестов.

**Подмена источника.** При `resolve_stream` для трека из группы (см. §5): кандидаты = связанные ID группы, отсортированные по приоритету их провайдера, сначала тот, что уже лежит в сохранённом/кэше. Пробуем по очереди, переходим к следующему на `Unavailable`, `UnsupportedQuality`, `NotFound`, `Auth` (провайдер без входа пропускается), `Network`/`RateLimited` — только если следующий кандидат у другого провайдера. Неопределённые ошибки (`Uncertain`, `ApiChanged`) — тоже переход, с логом. Какой источник реально заиграл, видно в панели «Сейчас играет» (уже есть строка «Яндекс Музыка · AAC 256»).

**Возможности с подменой.** Действие, требующее возможности (радио, тексты, страница исполнителя и т. п.), выполняется первым по приоритету провайдером с этой возможностью и входом (если вход нужен). Если таких нет — элемент интерфейса показывается неактивным с подсказкой «Подключите сервис с этой функцией».

**Поиск.** Запрос уходит всем вошедшим провайдерам с `search_*`. Без новых потоков на провайдер: запросы ставятся в существующий каталожный поток последовательно, результаты каждого провайдера отправляются в UI по мере прихода (чтобы первый ответ не ждал медленный сервис), затем склеиваются (§5). Фильтр по провайдеру — поле в результате, сам фильтр в UI — проект «интерфейс». Устаревшие ответы отбрасываются по существующему `view_generation`.

### 4. Профиль и аккаунты

Сейчас `Worker.account` = uid Яндекса и одновременно владелец истории, позиции воспроизведения, радио, загрузок и прав на офлайн. Разделяем:

- **Профиль** (`profile`) — локальный, всегда есть, создаётся при первом запуске (`settings.profile_id`). Владеет: историей, позицией воспроизведения (`playback`), локальными лайками, локальными плейлистами (следующий проект), отзывами для волны (проект «волна»).
- **Аккаунт провайдера** — `settings["account:<provider>"] = uid`. Владеет: правами на офлайн (`access`, `offline_owners`), записями `downloads.account`, очередью отчётов о прослушивании (`play_outbox`), радиосессией провайдера.

Миграция: существующий `account_uid:yandex` → `account:yandex`; строки `history`/`playback` с `account = <yandex uid>` переписываются на новый `profile_id`. `downloads`, `access`, `offline_owners`, `play_outbox`, `radio_play_intents` остаются привязаны к uid Яндекса.

Без входа: `record_play` пишет историю в профиль (сейчас при пустом аккаунте — молча ничего); сохранённые треки играют только при наличии прав соответствующего аккаунта, как и сейчас.

Команды `app`: `Login { provider: String, token: Token }` (заменяет `Login(Token)`), `Logout { provider: String, keep_saved: bool }`. `Logout` в этом проекте: забывает токен (keyring), сбрасывает `account:<provider>`, при `keep_saved = false` удаляет сохранённое этого аккаунта. **Лайки не трогает** (они наши; треки, которые больше неоткуда играть, показываются недоступными, пока не подключится сервис, где они есть). Плейлисты провайдера перестают показываться; предложить скопировать их в локальные перед выходом — решается в проекте «вход/выход», здесь нужна только команда копирования плейлиста провайдера в локальный (если локальные плейлисты к тому моменту готовы — иначе в том проекте). Вопрос пользователю «оставить сохранённое?» и экран — проект «вход/выход». `Restore` проверяет токены всех провайдеров с сохранённым токеном.

Событие состояния (`signed_in: bool`) заменяется на список `providers: Vec<ProviderStatus { id, name, auth, signed_in, capabilities }>`.

**Интерфейс в этом проекте — минимум:** экран входа по токену строится по списку провайдеров вместо захардкоженного Яндекса; элементы, для которых нет провайдера с возможностью, неактивны с подсказкой «Подключите сервис с этой функцией». Настройка порядка приоритета — только в `app` и настройках (`provider_order`), без экрана: при одном встроенном провайдере её не на чем показать; экран — проект «интерфейс». Склеенные строки поиска со списком источников — данные отдаются здесь, отрисовка — проект «интерфейс». Выход с вопросом «оставить сохранённое?» — проект «вход/выход».

### 5. Склейка треков и исполнителей

**Группа** — запись «один и тот же трек» с набором провайдерских ID. ID провайдера (`TrackId`) по-прежнему используется везде (очередь, кэш, загрузки, плейлисты) — менять формат идентификатора по всему коду не нужно. Группа — дополнительный слой поверх.

Схема `store`:
```sql
CREATE TABLE track_groups(track TEXT PRIMARY KEY, grp INTEGER NOT NULL, method TEXT NOT NULL); -- method: 'isrc' | 'meta' | 'self'
CREATE INDEX track_groups_grp ON track_groups(grp);
CREATE TABLE track_keys(key TEXT NOT NULL, track TEXT NOT NULL, PRIMARY KEY(key, track)); -- ключ сопоставления
CREATE TABLE artist_groups(artist TEXT PRIMARY KEY, grp INTEGER NOT NULL);
```

Правила (консервативные — лучше не склеить):
- Любой трек, попавший в `tracks`, получает группу (сам по себе — `self`).
- **По ISRC**: одинаковый ISRC у разных провайдеров → одна группа.
- **По метаданным**: ключ = нормализованное название + нормализованный основной исполнитель; совпадение ключа у треков **разных** провайдеров и разница длительности ≤ 2 с → одна группа. Нормализация: нижний регистр, Unicode NFKC, ё→е, убрать пунктуацию и лишние пробелы, убрать хвосты вида `(feat. …)`, `[Remastered 20xx]`, `- Radio Edit` **только** из ключа сравнения, но версии `Live`, `Remix`, `Acoustic`, `Instrumental` остаются частью ключа (это разные треки). Внутри одного провайдера треки никогда не склеиваются друг с другом.
- Треки одного провайдера в одной группе не допускаются: если сопоставление дало второй трек того же провайдера, группа не объединяется.
- **Исполнители** склеиваются, только если у них одинаковое нормализованное имя **и** хотя бы одна общая группа треков. Иначе — раздельно (тезки не слипаются).
- Сопоставление идёт при записи трека в `store` (синхронизация, поиск, открытие альбома) — без отдельных проходов в фоне.

Использование:
- Поиск: результаты разных провайдеров одной группы показываются одной строкой; отображается версия от провайдера с наивысшим приоритетом, у строки есть список источников.
- Подмена источника (§3) и лайки (§6) работают по группе.
- История, «нет повторов в плейлисте», «Все треки» исполнителя — используют группу (реализация в своих проектах).

### 6. Лайки

- Источник правды — локальная таблица `liked(grp INTEGER PRIMARY KEY, at INTEGER)` в профиле.
- Происхождение лайка не хранится: выход из провайдера лайки не удаляет, поэтому знать источник не нужно.
- Лайк/снятие лайка: запись в `liked` + задания в исходящую очередь (по образцу `play_outbox`; таблица `like_outbox(provider, track, liked, state, …)`) для каждого вошедшего провайдера с `likes`, у которого в группе есть трек. Отправка — в фоне, с повтором; `Uncertain` не повторяется автоматически (как у существующей очереди).
- Синхронизация: лайки провайдера подтягиваются и **добавляются** в `liked` (объединение). Снятие лайка у провайдера на стороне сервиса при синхронизации удаляет лайк локально, только если на прошлой синхронизации этот трек у провайдера был лайкнут, а локально лайк с тех пор не ставили заново (`at` раньше прошлой синхронизации). Лайк, который у провайдера никогда не стоял (например, отказались от отправки старых лайков), синхронизация не трогает. Точное правило — на исполнителе, с тестами.
- **Старые лайки в новый сервис — только с согласия.** Когда провайдер с `likes` подключается (или впервые появляется вход), `app` считает лайки из `liked`, у которых в группе есть трек этого провайдера и которых нет среди его лайков, и шлёт событие `LikesBackfillOffer { provider, count }`. Ничего не отправляется до команды `LikesBackfill { provider, accept: bool }`. Согласие запоминается для провайдера (`settings["likes_backfill:<provider>"]`): после «да» новые связи (трек нашёлся у этого провайдера позже, при поиске/синхронизации) отправляются сами; после «нет» — не отправляются, пока пользователь не включит это в настройках (решение исполнителя-ревью). Отправка пачкой через `like_outbox` с учётом `RateLimited`. Диалог в интерфейсе — проект «вход/выход».
- Лайки, поставленные в eagle после подключения, уходят во все подключённые провайдеры сразу (это не «старые» лайки).
- `replace_likes`/`DELETE … LIKE 'yandex:%'` удаляются; таблица `likes` мигрируется в `liked` через группы.
- Дизлайки остаются провайдерскими (нужны радио Яндекса); перенос в «наше» — проект «волна».

### 7. Перенос Яндекса

- `eagle-yandex` зависит только от `eagle-provider-sdk` (и HTTP через SDK), реализует `info()` с честными возможностями, `artist_tracks`, `isrc`, если API его отдаёт (проверить `contracts`; если нет — `isrc: false`).
- Все `eagle_yandex::…` в `app` уходят в `builtin()`. `prompt_token` из CLI — через `AuthMethod::Token`.
- Константы `LIKED_ALBUMS`/`LIKED_ARTISTS`/`ACCOUNT_UID` становятся ключами по `provider_id`.
- Тексты «создан в Яндекс Музыке» берут имя из `info().name`.

### 8. Проверки

- Юнит-тесты: нормализация и правила склейки (включая тезок, версии Live/Remix, один провайдер — не склеивается), подмена источника, выбор провайдера по возможности, порядок приоритета, миграции на копии реальной схемы.
- Интеграционные тесты `app` на двух `FakeProvider` (`fake-a`, `fake-b`): смешанная очередь, подмена при `Unavailable`, поиск со склейкой, лайк уходит в оба, выход одного провайдера не трогает данные другого.
- Тесты `eagle-yandex` через testkit на записанных ответах.
- Существующие тесты `session.rs` и `desktop_offline.rs` проходят (с правкой конструкторов).
- `cargo xtask bench` до и после: память и пробуждения в фоне не хуже базовой линии.
- Grep-проверка в CI или тест: в `crates/app`, `crates/store`, `crates/ui` нет строк `"yandex"` / `'yandex:` вне тестов и `builtin()`.

## Оставлено на исполнителя

- Как именно отдать HTTP провайдеру через SDK (свой трейт или тип из `eagle-net`), без утечки внутренностей `net`.
- Шаблон провайдера: каталог в `crates/providers/_template` или шаблон в `docs/`.
- Точные имена модулей и разбиение изменений в `session.rs` на коммиты; выносить из `session.rs` только то, что касается провайдеров и аккаунтов.
- Точное правило удаления лайков при синхронизации (§6) — с тестами на гонки «лайкнул локально / снял на сервере».
- Конкретная библиотека или ручная реализация NFKC — без тяжёлых зависимостей (`unicode-normalization` допустим).
- Порядок миграций и номер `user_version`.

## Вне этого проекта (порядок следующих)

1. Вход/выход: экран входа по провайдерам, «оставить сохранённое?», встроенный браузер.
2. История и плейлисты: история без повторов (группа, поднять наверх, засчитывать сразу при старте), локальные плейлисты с «+», без повторов, добавление тремя способами, перетаскивание плейлистов, синхронизация порядка с провайдером.
3. Своя волна: мгновенный старт, жанры/настроения, отзывы у нас.
4. Интерфейс: нижний плеер без «плавания» и с многоточием, поиск без прыжков, строка трека (без выделения, перетаскивание, анимация ▶), левая панель «Сейчас играет» с плавным выездом и быстрым переходом по «Далее», экран «Все треки» исполнителя с фильтрами и бесконечной прокруткой.

# Yandex Music: контракты desktop beta

Проверено 2026-11-13. Это исследование, а не утверждение о стабильном публичном API Яндекса. Официальной спецификации этих операций не найдено. Ниже ссылки на исходный код независимого неофициального клиента; его запросы являются свидетельством реализации клиента, но не подтверждают текущее поведение сервера или права аккаунта.

## Подтверждено в Eagle

Существующие тесты с локальным HTTP-сервером проверяют формирование запросов и разбор фиктивных ответов, в том числе создание и удаление плейлиста. Это не проверка API на реальном аккаунте. `Provider` сейчас не содержит контракта радиосессии, ревизии плейлиста или отправки истории.

Тест восстановления 100 загрузок заранее создаёт локальные PNG обложек и цвета, затем проверяет сохранённые URI и декодирование обоих размеров после аварийного завершения и офлайн-перезапуска. Загрузку обложек по сети этот тест не проверяет.

## Требуется ручная проверка на аккаунте

- Плейлисты: [исходник клиента](https://github.com/MarshalX/yandex-music-api/blob/main/yandex_music/_client_async/playlists.py) отправляет `POST /users/{uid}/playlists/{kind}/change` с `kind`, `revision`, `diff`; вставка использует track и album ID, удаление — диапазон позиций. Не проверены формат ошибок при конфликте, атомарность и актуальность этой схемы. Проверять только на новом уникальном тестовом плейлисте, созданном для проверки; после проверки удалить именно его. Дубли треков требуют позиционной идентификации.
- Радио: [исходник клиента](https://github.com/MarshalX/yandex-music-api/blob/main/yandex_music/_client_async/rotor_sessions.py) описывает создание сессии, получение следующей партии и события начала радио, начала, окончания и пропуска трека. `session_id` и `batch_id` нельзя смешивать между сессиями. Формат, доступность и обязательные поля нужно проверить отдельно. Автоматическая отправка feedback в рамках исследования не разрешена.
- История: [клиент](https://github.com/MarshalX/yandex-music-api/blob/main/yandex_music/_client_async/music_history.py) содержит чтение истории; это не доказательство контракта записи прослушивания. Нужны отдельные данные о записи и дедупликации. Не отправлять реальные события при исследовании.
- Доступ: `available=false`, отсутствие подписки, ошибки сети и отдельный 403 сами по себе не доказывают окончательную потерю доступа к сохранённому треку. До определения и проверки авторитетного сигнала результат `Unknown`.

В этом запуске credential для проверки аккаунта не был доступен, поэтому live-проверка не проводилась. Никакие плейлисты, лайки и события аккаунта не изменялись.

## Не реализовано / неопределённость повтора

Типы в `contracts.rs` — предложение границы. Экспериментальные методы `playlist_snapshot_unverified` и `edit_playlist_unverified` проверены только фиктивным HTTP-сервером и не подключены к интерфейсу; не считать их работоспособными на реальном сервере. Радио и отправка истории не реализованы до проверки протокола. Таймаут записи не означает, что сервер её отклонил: слепой повтор способен продублировать вставку или событие. После неоднозначного результата изменения плейлиста сначала получить свежий снимок и ревизию, сверить результат и сообщить о конфликте; не воспроизводить позиционную операцию автоматически. Для событий не доказан серверный ключ идемпотентности: локальный ID не даёт гарантии дедупликации, поэтому автоматический повтор после неоднозначного ответа также недопустим.

Лайки меняются только по явной команде. При ошибке ответа на запрос изменения интерфейс возвращает прежнее локальное состояние, хотя сервер мог принять запрос; до обновления с сервера фактическое состояние не подтверждено.

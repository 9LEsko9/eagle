# 0001. Логирование с этапа 0

Статус: принято. Дата: 2026-11-12.

## Контекст

Базовые замеры должны включать реальное логирование. Нужны ограниченная память,
файлы для публичных issues, приватность и отсутствие периодических пробуждений
при пустом буфере. Используем log с kv, без tracing.

## Решение

Небольшой собственный бэкенд в eagle-platform: общий mutex-буфер 64 КиБ,
поток eg-log с Condvar, секундный срок только при непустом буфере, два файла
по 1 000 000 байт. Warn/error дожидаются свободного места, затем записи и
sync_data; обычные записи при переполнении отбрасываются со счётчиком потерь.
Все сообщения ограничены 4096 байт плюс перевод строки. Файловые ошибки
доступны вызывающему коду через Logger::flush.

Token и SignedUrl живут в eagle-core и маскируют Display/Debug. Бэкенд повторно
маскирует известные параметры/заголовки без regex, до вывода в любой sink.
На info допускаются идентификаторы и провайдеры; названия и запросы запрещены.

Desktop пишет также в stderr, Android — через android_logger 0.15,
iOS — через oslog 0.2. Мобильная оболочка передаёт приватный каталог.
Logger::report возвращает два файла после синхронного сброса.
Rust panic hook пишет сам, включая backtrace, без очереди писателя.

## Почему

Сравнили изолированные release-пробы одинаковыми профилями (fat LTO,
codegen-units=1, panic=abort, strip=true) на macOS arm64, Rust 1.99.1,
log 0.4.35. Команда: `python3 bench/compare_loggers.py --seconds 60`.
Значения памяти — конечный phys_footprint, CPU — процент одного ядра за минуту;
это один прогон, не универсальные пределы. Собственный probe использует тот же
бэкенд, включая panic hook. Info-сценарий пишет 1 событие/с с полями.

| Бэкенд | Release, байт | Память idle, байт | CPU idle, % | Память info, байт | CPU info, % |
| --- | ---: | ---: | ---: | ---: | ---: |
| Пустой процесс | 302608 | 1130880 | 0 | — | — |
| Собственный | 370080 | 1180032 | 0 | 1278336 | 0.0004321 |
| flexi_logger 0.31.10 | 552816 | 1556888 | 0.0000877 | 1655192 | 0.0002879 |

Собственный бэкенд в этой пробе меньше flexi_logger на 182736 байт по бинарнику
и на 376856 байт по idle-памяти. Он выбран по этим замерам и поведению очереди. В info-сценарии CPU у flexi_logger
оказался немного ниже; один прогон с такими малыми числами не доказывает
преимущества по CPU ни у одного из бэкендов.

У flexi_logger проверялся BufferAndFlushWith(65536, 1 секунда), файловая ротация
и Duplicate::All на stderr, default-features=false. Его штатный буферный режим
использует регулярный flush-поток; асинхронный режим использует неограниченный
канал. Источники: [WriteMode](https://docs.rs/flexi_logger/0.31.10/flexi_logger/enum.WriteMode.html),
[примеры](https://docs.rs/flexi_logger/0.31.10/flexi_logger/code_examples/index.html).
Для соблюдения требований пришлось бы дополнительно менять механизм ожидания
и ограничения очереди, поэтому преимущество готовой ротации невелико.

## Последствия и проверка

Ротацию и конкурентную запись поддерживаем сами. Есть тесты маскировки на двух
уровнях, kv, переполнения/счётчика потерь, фильтров, двух файлов, таймера,
синхронных warn и записи паники без писателя. Отдельный дочерний процесс
проверяет установленный hook, stderr, отчёт и изменение фильтра из настроек.
CI запускает idle и info benchmark на трёх ОС; Linux проверяет нулевую разницу
voluntary switches потока eg-log в idle. Мобильные адаптеры проходят cargo check;
доставка в logcat/os_log требует последующего теста на устройствах.

Синхронные warn/error могут задержать вызывающий поток на время диска.
Ошибки диска, авария C-кода, abort и принудительное завершение не исправляются
panic hook; последние несброшенные info могут потеряться. Backtrace ограничен
4096 байт, в stripped release возможны только адреса. Один каталог логов
предназначен для одного экземпляра приложения. Последующие изменения
бэкенда измеряем заново на той же машине; CSV остаются в bench/results/ локально
и в артефактах CI.

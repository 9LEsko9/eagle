# eagle-provider-sdk

Граница между приложением и музыкальными сервисами. Провайдер — отдельный крейт,
который реализует трейт `Provider` из этого SDK. Приложение работает только с трейтом.

## Как написать провайдер

Шаблон для копирования: `crates/providers/_template` (`eagle-provider-template`).

Правила:

- **Зависимость только от `eagle-provider-sdk`.** Не добавляйте клиентов HTTP, очередей
  и прочих крейтов без крайней необходимости: HTTP-запросы идут через трейт `Http`, который
  передаёт хост. Так провайдер получает общие повторы, лимиты, прокси и пул потоков.
- **Без собственных потоков.** Все методы блокирующие и вызываются хостом на его рабочих потоках.
- **Ничего не логировать из секретов.** `Token` и `SignedUrl` выводятся как `[REDACTED]`
  и `[REDACTED URL]`. Значение извлекается через `expose()` только там, где оно нужно для запроса
  (заголовок, форма, URL). Текст ошибок и логи не должны содержать токен, ссылку или подписи.
- **Токен не хранить на диске.** Хост вызывает `login`, `restore` и `logout`. Провайдер может
  держать токен в памяти на время работы и должен забыть его в `logout`.
- **Способы входа объявляются в `info().sign_in`.** См. раздел «Вход в аккаунт» ниже.
- **Курсоры непрозрачны.** `next` и `cursor` — строки, которые провайдер выдаёт и принимает
  сам. Хост и приложение их не разбирают и не сохраняют между запусками.
- **Возможности честные.** `info().capabilities` описывает то, что провайдер умеет в принципе.
  Флаг включается только тогда, когда соответствующий метод реально работает. Если аккаунту
  что-то недоступно, это выражается в `Account::capabilities`, а не в `info()`.
- **Идентификаторы.** `TrackId` имеет вид `provider:local`. Префикс — `info().id`, только `[a-z]+`.
  Локальная часть — `[A-Za-z0-9_-]`, длина всей строки до 200 символов.
- **Ошибки.** Используйте варианты `ProviderError`. `Unavailable` означает регион, подписку
  или удалённый трек, и только его приложение использует для перехода к другому провайдеру.

## Радио («Моя волна»)

`radio_start(&RadioTuning)` начинает волну, `radio_next` просит следующую партию. Настройка
`RadioTuning`: `mood` — валентность (x) и энергия (y) в `-1.0..=1.0` (`None` — любое
настроение), `novelty` — от `0.0` (знакомое) до `1.0` (новое), `seed` — трек, от которого
начинается волна («Ещё такого»). Настройка по умолчанию — обычная волна без уточнений.

- Возможность `radio` — волна вообще; `radio_tuning` — провайдер учитывает `mood` и `novelty`;
  `radio_seed` — учитывает `seed`. Приложение передаёт `mood` и `novelty` только провайдеру с
  `radio_tuning`, а `seed` — провайдеру трека; провайдер без `radio_seed` отвечает ошибкой
  без обращения к сети. Не заявляйте флаг, пока метод не работает.
- Восемь направлений настроения (`RadioTuning::mood_direction`, против часовой стрелки от
  положительной валентности): светлое, весёлое, энергичное, дерзкое, мрачное, грустное,
  тихое, спокойное. Вектор короче `MOOD_DEAD_ZONE` — «любое настроение». Новизна делится на
  `NoveltyBand` по границам `NOVELTY_FAMILIAR` и `NOVELTY_NEW`. Провайдер сам сводит это к
  тому, что умеет сервис; соответствие документируйте (для Яндекса — `docs/yandex-contracts.md`).
- Приложение считает настройку применённой со следующего трека: текущий трек играет дальше,
  очередь после него заменяется партией новой сессии. «Не то» — `set_disliked` (если есть
  `dislikes`) и переход к следующему треку.
- В тестах используйте `FakeProvider`: он записывает настройки (`radio_tunings`), начинает
  волну с `seed` и отвечает `Unavailable` на то, чего нет в его возможностях.

## Вход в аккаунт

`ProviderInfo::sign_in` — список способов входа (`SignInMethod`), предпочтительный первым.
Пустой список значит, что каталог работает без входа (`ProviderInfo::needs_sign_in()` ложно).
Приложение показывает в «Настройки → Сервисы» первый способ, остальные предлагает ссылками
рядом, в порядке списка. Названия сервисов и тексты способов приложение берёт из `ProviderInfo`.

| Способ | Что делает пользователь | Методы провайдера |
| --- | --- | --- |
| `Token { hint, help_url }` | вставляет токен в поле; `hint` подписывает поле, `help_url` ведёт на страницу «Где взять токен» | `login` |
| `DeviceCode` | вводит короткий код на странице провайдера с любого устройства (OAuth device flow) | `sign_in_start`, `sign_in_continue` |
| `Password { login_hint }` | вводит логин и пароль, затем, возможно, второй фактор | `sign_in_start`, `sign_in_continue` |
| `Browser` | входит на странице провайдера в системном браузере | `sign_in_start`, `sign_in_continue` |

Многошаговый вход устроен как цикл шагов `SignInStep`; провайдер сам не спит и не создаёт потоков,
хост ждёт и опрашивает его на отдельном потоке (не на потоке каталога):

1. `sign_in_start(method, input)` возвращает первый шаг. `SignInInput::Password { login, password }`
   передаётся только для `Password`, для остальных способов — `SignInInput::None`.
2. `ShowCode { code, url, interval, expires_in, flow }`: хост показывает код и ссылку, затем вызывает
   `sign_in_continue(&flow, None)` не чаще, чем раз в `interval`, пока не пройдёт `expires_in`.
3. `OpenBrowser { url, interval, flow }`: хост открывает ссылку и опрашивает так же (с запасом
   в десять минут).
4. `SecondFactor { hint, flow }`: хост просит код (`hint` говорит, откуда его взять) и вызывает
   `sign_in_continue(&flow, Some(code))`.
5. `Pending` — вход не завершён, опросить снова. `Expired` — код или вход устарел, начать заново.
6. `Done(token)`: хост передаёт токен в `login` и сохраняет его так же, как токен, введённый
   вручную. Сам провайдер токен не хранит.

Правила:

- `SignInFlow` — непрозрачное состояние шага в памяти (например, `device_code`). Его не хранят,
  не показывают и не логируют; пользовательский код (`code`) и ссылка тоже не попадают в логи.
- Способ, которого нет в `info().sign_in`, возвращает `Unavailable` без обращения к сети.
  `Token` через `sign_in_start` не запускается.
- Ошибка неверного пароля, кода или отказа — `ProviderError::Auth`; сеть — `Network`. Приложение
  само подбирает пользовательский текст («Не получилось войти», «Нет связи с сервисом»).
- `Account::name` — имя аккаунта (логин или отображаемое имя); приложение показывает его под
  названием сервиса. Если имени нет, поле `None`.
- Если сервис отвечает на ошибку авторизации кодом 4xx с объяснением в теле (например,
  `authorization_pending` у OAuth), задайте `Request::error_body = true`: тогда хост вернёт такой
  ответ как `Response` с телом, а не `HttpError::Status`. По умолчанию 4xx остаётся ошибкой.

## Как проверить провайдер (testkit)

Фича `testkit` добавляет `FakeProvider` (провайдер в памяти с настраиваемым каталогом,
входом и отказами) и `testkit::conformance` (проверки соответствия).

```toml
[dev-dependencies]
eagle-provider-sdk = { path = "../../provider-sdk", features = ["testkit"] }
```

```rust
use eagle_provider_sdk::testkit::conformance::{self, Fixtures};

let violations = conformance::run(&provider, &Fixtures {
    known_track: "acme:1".parse()?,
    query: "song".into(),
    artist: Some("acme:artist-1".parse()?),
    signed_in: true,
});
assert!(violations.is_empty(), "{violations:?}");
```

Проверки:

- `info`: id — `[a-z]+`, name не пустой;
- все `Track.id` из поиска и лайков проходят `TrackId::from_str` и принадлежат провайдеру;
- заявленная возможность не возвращает `Unavailable`; если нужен вход, а `signed_in = false`,
  ответы `Auth` не считаются нарушением;
- пагинация поиска и лайков конечна (не более 100 страниц);
- `resolve_stream(known_track, Standard)` даёт непустой URL и срок жизни в будущем;
- если заявлен `isrc`, хотя бы один трек из поиска содержит ISRC;
- способы входа, которых нет в `info().sign_in` (`DeviceCode`, `Password`, `Browser`), возвращают
  `Unavailable` из `sign_in_start` (без сети; входит в `run`).

`conformance::check_sign_in(&provider)` отдельно запускает заявленные `DeviceCode` и `Browser`:
`sign_in_start` должен вернуть `ShowCode` (непустые `code` и `url`, ненулевые `interval` и
`expires_in`) или `OpenBrowser` (непустая ссылка, ненулевой `interval`). Эта проверка обращается
к сервису, поэтому она вынесена из `run`: вызывайте её в тесте, который отвечает записанными
или локальными ответами.

`FakeProvider` умеет сценарии входа: `with_device_code(n)` (`ShowCode`, затем `Pending` `n` раз и
`Done(FAKE_SIGN_IN_TOKEN)`), `expiring()` (поток заканчивается `Expired`), `with_password(second_factor)`
(пароль `FAKE_WRONG_PASSWORD` отклоняется, второй фактор — `FAKE_SECOND_FACTOR`),
`with_browser_sign_in(n)`, `with_sign_in_timing(interval, expires_in)`; счётчики
`sign_in_starts()` и `sign_in_polls()` показывают, сколько раз вызывались методы.

Запускайте проверки на записанных ответах сервиса, а не на живом аккаунте в обычных тестах.
Если проверки нельзя запустить полностью, по крайней мере проверяйте `conformance::check_info`.

## Записать ответы для своего провайдера

Проверку соответствия можно прогнать на записанных ответах сервиса, без живого аккаунта
в обычных тестах. Пример полного набора — `crates/providers/yandex/tests/conformance.rs`.

1. Напишите очистку ответов: `fn scrub(path: &mut String, body: &mut serde_json::Value)`.
   Она заменяет в пути и в ответе всё, что относится к аккаунту (id, логин, почту, имя, телефон),
   и урезает длинные списки лайков и плейлистов. Очистка должна быть идемпотентной:
   повторный вызов ничего не меняет. Образец — `eagle_yandex::scrub_recording`.
2. Добавьте тест записи под `#[ignore]`: настоящий `Http` (например, `eagle_net::Client`)
   оборачивается в `RecordingHttp::new(inner, dir, scrub)`, токен берётся из переменной окружения.
3. Запишите ответы вручную, на своей машине. Для Яндекса команда такая:
   `EAGLE_YANDEX_TOKEN=<токен> cargo test -p eagle-yandex --test conformance -- --ignored record`.
4. Просмотрите файлы: `git diff --stat` и выборочно глазами. В них не должно быть токена,
   uid, логина, почты, имени, телефона или медиатеки сверх нескольких элементов.
5. Проверка на записях: `ReplayHttp::open(dir)` → `Provider::login` → `conformance::run`.
   Если записей нет, тест должен пропускаться с сообщением, а не проходить молча.

Что пишется в файлы. Каждый ответ — `NNN-<метод>-<путь>.json` с полями `method`, `path`,
`query`, `status` и `body` (JSON) или `body_base64` (остальное). Заголовки и `Request.token`
не записываются никогда; найденное в ответе или пути значение токена заменяется на `[REDACTED]`.
Из query убираются параметры-подписи (ключи, содержащие `sig`, `token`, `auth`, `key`,
`secret`, `credential`). Одинаковые запросы отдаются в порядке записи; когда записи кончаются,
повторяется последняя. Ответ с кодом 4xx воспроизводится как `HttpError::Status`.

## Как зарегистрировать провайдер

1. Добавьте крейт в `members` корневого `Cargo.toml`.
2. Добавьте одну строку в `builtin()` в `crates/app/src/providers.rs`: там создаётся
   экземпляр провайдера.
3. Добавьте исключение лицензии в `deny-ios.toml` по образцу соседних крейтов, если крейт
   использует `GPL-3.0-or-later`.

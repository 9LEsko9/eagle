# eagle-provider-sdk

Граница между приложением и музыкальными сервисами. Провайдер — отдельный крейт,
который реализует трейт `Provider` из этого SDK. Приложение работает только с трейтом.

## Как написать провайдер

Шаблон для копирования: `crates/providers/_template` (`eagle-provider-template`).

Правила:

- **Зависимость только от `eagle-provider-sdk`.** Не добавляйте клиентов HTTP, очередей
  и прочих крейтов без крайней необходимости: HTTP-запросы идут через трейт `Http`, который
  передаёт хост. Так провайдер получает общие повторы, лимиты, прокси и пул потоков.
- **Без собственных потоков.** Все методы блокирующие и вызываются хостом на его рабочих потоках.
- **Ничего не логировать из секретов.** `Token` и `SignedUrl` выводятся как `[REDACTED]`
  и `[REDACTED URL]`. Значение извлекается через `expose()` только там, где оно нужно для запроса
  (заголовок, форма, URL). Текст ошибок и логи не должны содержать токен, ссылку или подписи.
- **Токен не хранить на диске.** Хост вызывает `login`, `restore` и `logout`. Провайдер может
  держать токен в памяти на время работы и должен забыть его в `logout`.
- **Курсоры непрозрачны.** `next` и `cursor` — строки, которые провайдер выдаёт и принимает
  сам. Хост и приложение их не разбирают и не сохраняют между запусками.
- **Возможности честные.** `info().capabilities` описывает то, что провайдер умеет в принципе.
  Флаг включается только тогда, когда соответствующий метод реально работает. Если аккаунту
  что-то недоступно, это выражается в `Account::capabilities`, а не в `info()`.
- **Идентификаторы.** `TrackId` имеет вид `provider:local`. Префикс — `info().id`, только `[a-z]+`.
  Локальная часть — `[A-Za-z0-9_-]`, длина всей строки до 200 символов.
- **Ошибки.** Используйте варианты `ProviderError`. `Unavailable` означает регион, подписку
  или удалённый трек, и только его приложение использует для перехода к другому провайдеру.

## Как проверить провайдер (testkit)

Фича `testkit` добавляет `FakeProvider` (провайдер в памяти с настраиваемым каталогом,
входом и отказами) и `testkit::conformance` (проверки соответствия).

```toml
[dev-dependencies]
eagle-provider-sdk = { path = "../../provider-sdk", features = ["testkit"] }
```

```rust
use eagle_provider_sdk::testkit::conformance::{self, Fixtures};

let violations = conformance::run(&provider, &Fixtures {
    known_track: "acme:1".parse()?,
    query: "song".into(),
    artist: Some("acme:artist-1".parse()?),
    signed_in: true,
});
assert!(violations.is_empty(), "{violations:?}");
```

Проверки:

- `info`: id — `[a-z]+`, name не пустой;
- все `Track.id` из поиска и лайков проходят `TrackId::from_str` и принадлежат провайдеру;
- заявленная возможность не возвращает `Unavailable`; если нужен вход, а `signed_in = false`,
  ответы `Auth` не считаются нарушением;
- пагинация поиска и лайков конечна (не более 100 страниц);
- `resolve_stream(known_track, Standard)` даёт непустой URL и срок жизни в будущем;
- если заявлен `isrc`, хотя бы один трек из поиска содержит ISRC.

Запускайте проверки на записанных ответах сервиса, а не на живом аккаунте в обычных тестах.
Если проверки нельзя запустить полностью, по крайней мере проверяйте `conformance::check_info`.

## Записать ответы для своего провайдера

Проверку соответствия можно прогнать на записанных ответах сервиса, без живого аккаунта
в обычных тестах. Пример полного набора — `crates/providers/yandex/tests/conformance.rs`.

1. Напишите очистку ответов: `fn scrub(path: &mut String, body: &mut serde_json::Value)`.
   Она заменяет в пути и в ответе всё, что относится к аккаунту (id, логин, почту, имя, телефон),
   и урезает длинные списки лайков и плейлистов. Очистка должна быть идемпотентной:
   повторный вызов ничего не меняет. Образец — `eagle_yandex::scrub_recording`.
2. Добавьте тест записи под `#[ignore]`: настоящий `Http` (например, `eagle_net::Client`)
   оборачивается в `RecordingHttp::new(inner, dir, scrub)`, токен берётся из переменной окружения.
3. Запишите ответы вручную, на своей машине. Для Яндекса команда такая:
   `EAGLE_YANDEX_TOKEN=<токен> cargo test -p eagle-yandex --test conformance -- --ignored record`.
4. Просмотрите файлы: `git diff --stat` и выборочно глазами. В них не должно быть токена,
   uid, логина, почты, имени, телефона или медиатеки сверх нескольких элементов.
5. Проверка на записях: `ReplayHttp::open(dir)` → `Provider::login` → `conformance::run`.
   Если записей нет, тест должен пропускаться с сообщением, а не проходить молча.

Что пишется в файлы. Каждый ответ — `NNN-<метод>-<путь>.json` с полями `method`, `path`,
`query`, `status` и `body` (JSON) или `body_base64` (остальное). Заголовки и `Request.token`
не записываются никогда; найденное в ответе или пути значение токена заменяется на `[REDACTED]`.
Из query убираются параметры-подписи (ключи, содержащие `sig`, `token`, `auth`, `key`,
`secret`, `credential`). Одинаковые запросы отдаются в порядке записи; когда записи кончаются,
повторяется последняя. Ответ с кодом 4xx воспроизводится как `HttpError::Status`.

## Как зарегистрировать провайдер

1. Добавьте крейт в `members` корневого `Cargo.toml`.
2. Добавьте одну строку в `builtin()` в `crates/app/src/providers.rs`: там создаётся
   экземпляр провайдера. Файл появится в следующей задаче плана (Task 5, «Реестр `Providers`»);
   до этого регистрации нет.
3. Добавьте исключение лицензии в `deny-ios.toml` по образцу соседних крейтов, если крейт
   использует `GPL-3.0-or-later`.

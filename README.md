# Eagle

Pre-alpha.

Rust workspace: core, providers/yandex, providers/vk, net, store, engine,
palette, platform, app, ui; бинарники eagle-cli и eagle-desktop.
CLI реализует Яндекс Музыку и локальный аудиокэш. UI и сетевой провайдер VK пока не реализованы.

## Яндекс Музыка из CLI

Для проверки нужен отдельный тестовый аккаунт с доступом к Яндекс Музыке.
Получите OAuth-токен по [инструкции автора Yandex Music API](https://ym.marshal.dev/token/).
Вход через пароль Яндекса внутри eagle не реализован. Выполните login и вставьте
только токен в скрытый интерактивный ввод. Не передавайте его аргументом команды,
не сохраняйте в config и не отправляйте в issue. После проверки `/account/status`
токен сохраняется в системном keyring (macOS Keychain, Windows Credential Manager,
Linux Secret Service). На Linux нужна работающая пользовательская D-Bus-сессия и
разблокированное хранилище секретов.

```sh
cargo run -p eagle-cli -- yandex login
cargo run -p eagle-cli -- yandex status
cargo run -p eagle-cli -- yandex search "исполнитель трек"
cargo run -p eagle-cli -- play yandex:123
# Та же команда поддерживается с префиксом yandex:
cargo run -p eagle-cli -- yandex play yandex:123
# Закрепить полную копию от вытеснения:
cargo run -p eagle-cli -- play yandex:123 --save
# Диагностика загрузки без аудиоустройства:
cargo run -p eagle-cli -- play yandex:123 --download-only
```

Замените `yandex:123` на ID из поиска. По умолчанию выбирается полный MP3 до
320 кбит/с, `--standard` ограничивает выбор 192 кбит/с. Preview не выбирается.
Протокол опирается на [реализацию DownloadInfo](https://github.com/MarshalX/yandex-music-api/blob/main/yandex_music/download_info.py).
Спайка этапа 1 в этом репозитории нет: поддержка lossless и шифрованного API пока
не заявляется. 2026-11-12 владелец подтвердил живой вход, поиск, звук и повторное
воспроизведение без интернета для тестового трека. Локальные HTTP-тесты отдельно
проверяют обновление истёкшей ссылки; принудительное истечение ссылки на живом API
не проверялось.

CLI сначала ищет закреплённую копию (любого качества), затем кэш нужного качества.
При попадании в кэш не запрашивает токен, метаданные или URL. На сетевом пути весь
трек загружается перед запуском звука диапазонами по 2 МиБ; во время воспроизведения
сетевые потоки спят на Condvar. Это увеличивает задержку первого запуска.
После успешной загрузки CLI печатает число HTTP-заданий и байты прочитанных тел
ответов. Повторный запуск должен показать `0 запросов, 0 байт ответов` и работать
при отключённой сети. Эти счётчики не включают заголовки/TLS/TCP и не являются
измерением пробуждений радиомодуля. HTTP 401/403/410 у аудиоссылки вызывает
повторный resolve с ограниченным числом попыток. Истёкший OAuth-токен требует login.

Другие команды: `yandex likes`, `playlists`, `album yandex:ID`,
`playlist yandex:OWNER_KIND`, `like yandex:ID`, `unlike yandex:ID`,
`dislike yandex:ID`, `undislike yandex:ID`, `sync`.
Unlike снимает лайк; dislike ставит отдельную отметку «не рекомендовать».
Синхронизация выполняется после login, своих лайков/дизлайков и по `sync`.
Для CLI отдельного события возврата в окно нет; cached play намеренно не запускает
синхронизацию. ID лайков забираются одним ответом API, полные треки — пачками
по 100 без лимита в 10 000. Список плейлистов API отдаёт целиком.

## Хранилище и восстановление

Данные находятся рядом с logs в каталоге Eagle; `EAGLE_DATA_DIR` меняет корень.
SQLite работает в WAL с `user_version=1`; записи выполняет один `eg-store`,
чтения открывают короткоживущие read-only соединения. Схема содержит треки,
альбомы, исполнителей, плейлисты, лайки, кэш, палитры и настройки.
Кэш ограничен 2 ГиБ; незакреплённые файлы вытесняются по последнему обращению.
Сохранённые копии учитываются в лимите; если весь лимит закреплён, загрузка
останавливается с объяснением. Обложки сохраняются только в размерах до 64 и
600 px, палитра получается медианным сечением по 32×32 и записывается один раз.

У аудиофайла есть JSON-карта полузакрытых диапазонов `[start,end)`, размера,
ETag и флага закрепления. Байты синхронизируются до атомарной замены карты.
Дыры никогда не считаются загруженными; повреждённая карта и её аудиофайл
отбрасываются при открытии кэша. Незавершённая загрузка с ETag продолжается после
обрыва, без ETag начинается заново. При ошибке записи (включая отсутствие места)
скачивание прекращается; неуспешный диапазон не публикуется в SQLite.
Повреждённая SQLite сохраняется как `corrupt-*.sqlite`, создаётся новая база,
кэш и закрепления восстанавливаются из карт. Метаданные восстанавливает `sync`;
новую неизвестную версию схемы приложение не перезаписывает.

Решение для текущего CLI: аудио на диске **не шифруется**. На Unix корень данных
имеет права 0700; шифрование ключом из keyring остаётся отдельным продуктовым
решением. Текущая версия не обеспечивает ограничение «офлайн только внутри eagle».
Перемотка во время сетевой загрузки и управление очередью из CLI пока отсутствуют;
модель очереди принимает ID разных провайдеров и пропускает недоступные треки.
Одновременные процессы с общим каталогом данных пока не поддерживаются.

## Разработка

Rust edition 2024, MSRV 1.89 (поднят для исправленной SQLite).
На Linux для сборки нужны `libasound2-dev`, `libdbus-1-dev` и `pkg-config`. Общие зависимости: thiserror и log; tracing запрещён.

```sh
cargo fmt --all --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
cargo deny check licenses bans sources
cargo audit
cargo build --profile profiling
```

## Замеры

Нужен Python 3.9+.
`cargo xtask bench --scenario store` измеряет 1000 записей SQLite, открытый
кэш и 100 RGB-миниатюр 64×64 в памяти, без сети. Сравнивайте с `--scenario idle`
на той же машине. Это фиксированная синтетическая нагрузка, а не пользовательская
медиатека. Baseline этапа 1 отсутствует; сравнение с ним остаётся открытым.
Локальный замер 2026-11-12: macOS 27.2 arm64, Rust 1.99.1, Python 3.15.0,
release, последовательные окна по 60 с. Этап 0 собран из `40d77d4` в отдельном
каталоге; для обеих версий использован один текущий замерщик с `--binary`.

| Сценарий | phys_footprint, байт | CPU, % одного ядра | CPU idle wakeups | Interrupt wakeups |
| --- | ---: | ---: | ---: | ---: |
| Этап 0, idle (`40d77d4`) | 1 180 032 | 0 | 0 | 0 |
| Текущий CLI, idle | 1 786 264 | 0 | 0 | 0 |
| Текущий CLI, SQLite + 100 миниатюр | 4 161 968 | 0 | 0 | 0 |

Рост idle-памяти относительно этапа 0 — 606 232 байт. Release-бинарник вырос
с 370 096 до 5 313 776 байт. Это единичные локальные прогоны, не статистический
анализ регрессий; baseline этапа 1 ими не заменяется. CSV остаются локально в
`bench/results/` (исключены из Git).

`cargo xtask bench` собирает release eagle-cli и измеряет
сценарий idle с включённым логгером за 60 секунд.
`cargo xtask bench --scenario info` измеряет одну info-запись в секунду,
включая структурированные поля, маскировку, файл и stderr. `cargo xtask bench --seconds 2` — smoke-проверка.
CSV сохраняется в bench/results/ и содержит также размер release-бинарника. CPU — доля одного ядра по разнице процессорного
времени; память — конечный снимок, не пик. Linux: PSS; macOS: phys_footprint;
Windows: private working set. Linux: разница voluntary_ctxt_switches по всем
живым потокам, суммарно и в отдельном threads.csv. Это прокси пробуждений,
а не точный счётчик sched_wakeup; завершившиеся между снимками потоки
не наблюдаются. CSV отмечает исчезнувшие потоки и неполное окно новых потоков. CI сохраняет оба сценария как CSV-артефакты по каждой ОС. На Linux idle
дополнительно проверяет нулевую разницу voluntary switches у потока eg-log.

Для реального трека:

```sh
cargo xtask bench --scenario track --track yandex:128582477
```

Этот сценарий использует токен из keyring и отдельный временный каталог:
первый запуск скачивает трек целиком, второй обязан прочитать его без HTTP.
Звук не включается, пользовательский кэш не меняется.
Локальный прогон 2026-11-12 для `yandex:128582477` (аудио 3 707 298 байт):

| Запуск | Время, с | HTTP-запросы | Тела ответов, байт | Наблюдавшийся пик памяти, байт |
| --- | ---: | ---: | ---: | ---: |
| Первая загрузка | 7,104 | 8 | 3 929 622 | 12 190 152 |
| Чтение кэша | 0,033 | 0 | 0 | 2 539 952 |

В первой строке 243 снимка памяти, во второй только 2; пик короткого запуска
легко пропустить. Между первым и последним снимком холодного запуска зарегистрированы
0 package-idle и 5 interrupt wakeups, для cached — 0 и 0. Это CPU-метрики процесса
за наблюдавшийся интервал, не радиопробуждения за весь трек.

В `.track.csv` записываются
время запуска до завершения загрузки, число HTTP-запросов (включая редиректы),
байты прочитанных тел ответов и размер аудиофайла. Память опрашивается каждые
25 мс: `sampled_peak_*` — наблюдавшийся максимум, не точный пик ОС.
Быстрый cached-запуск может не попасть в выборку; пустое поле означает отсутствие
измерения. Время звучания и нагрузка декодирования в этот сценарий не входят.

`--binary /путь/к/eagle-cli` позволяет использовать уже собранный бинарник,
включая baseline, без повторной сборки. Сам замерщик не меняет версии кода.
На macOS CSV также содержит разницы `ri_pkg_idle_wkups` и `ri_interrupt_wkups`
из [Apple rusage_info_v2](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/resource.h).
Это счётчики CPU-пробуждений процесса, не включений Wi-Fi/LTE.
В track-сценарии они относятся только к интервалу между первым и последним
снимком (`sampled_window_seconds`); при менее двух снимках поля пустые.
Ни они, ни число HTTP-запросов не доказывают сон радиомодуля. Прямой замер
радиопробуждений требует отдельной методики/телеметрии устройства и остаётся открытым.

Для нагрузки во время звучания есть отдельный сценарий (трек должен уже лежать
целиком в кэше; команда включает звук):

```sh
cargo xtask bench --scenario playback --track yandex:128582477 --seconds 20 \
  --data-dir "$HOME/Library/Application Support/eagle"
```

Первые 2 с исключаются как прогрев, затем измеряется CPU за заданное окно,
память в конце окна и пробуждения процесса. После окна воспроизведение
останавливается. HTTP-запросов должно быть 0; неполный кэш или раннее завершение
трека считаются ошибкой замера. `--binary target/debug/eagle-cli` позволяет тем же
сценарием сравнить debug. Декодер MP3, rodio и eagle-engine оптимизированы и в
профиле dev; остальной workspace сохраняет обычную отладочную сборку.

Локальное сравнение во время звучания MP3 `yandex:128582477` из кэша на M2:
по одному окну 20 с после 2 с прогрева, один и тот же файл и аудиотракт.

| Сборка | CPU, % одного ядра | phys_footprint, байт | HTTP-запросы |
| --- | ---: | ---: | ---: |
| Debug до оптимизации | 18.61 | 6 095 520 | 0 |
| Debug с оптимизацией аудиокрейтов | 1.34 | 5 669 560 | 0 |
| Release | 1.18 | 5 456 544 | 0 |

Оптимизация снижает CPU debug примерно в 14 раз в этой пробе. Это короткий
локальный замер одного MP3; другие кодеки и устройства отдельно не измерялись.
В release не добавлялись новые преобразования сигнала или изменения буфера.

Поправка единиц CPU (2026-11-12): `proc_pid_rusage` возвращает время в Mach ticks,
которые переводятся через `mach_timebase_info`. На этой M2 коэффициент равен
125/3 нс на tick. Старые ненулевые CPU-значения из macOS CSV были занижены в
41,67 раза; память, сетевые счётчики и нулевые дельты CPU этим не затронуты.
Сэмплер теперь проверяется против независимого `time.process_time()`;
старые файлы результатов не переписаны. Поправка также внесена в ADR логирования.

## Логирование с этапа 0

Фасад `log` с `kv`, собственный бэкенд в `eagle-platform::logging`, без tracing.
В релизе статический максимум debug (`release_max_level_debug`); trace доступен
только в debug-сборке. По умолчанию info. Например,
`EAGLE_LOG=info,eagle_net=debug` включает debug для крейта и его модулей.
`Logger::set_filter` меняет те же правила из будущих настроек; `off` отключает вывод.

CLI и desktop инициализируют логгер при запуске. Файлы `eagle.log` и
`eagle.previous.log` ограничены 1 000 000 байт каждый. Каталог: Linux —
`$XDG_DATA_HOME/eagle/logs` или `~/.local/share/eagle/logs`, Windows —
`%LOCALAPPDATA%/eagle/logs`, macOS — `~/Library/Application Support/eagle/logs`.
`EAGLE_DATA_DIR` переопределяет каталог данных (логи в его подпапке logs).
Мобильная оболочка передаёт свой приватный каталог в `Logger::init`.
Десктоп дублирует записи в stderr, Android — через android_logger в logcat,
iOS — в os_log. `Logger::report` синхронно сбрасывает буфер и возвращает оба
файла для будущей кнопки «Скопировать отчёт». Одновременный запуск нескольких
экземпляров с одним каталогом логов пока не поддерживается.

Общий буфер под mutex — 64 КиБ, запись — максимум 4096 байт плюс перевод строки.
Переполнение отбрасывает запись и добавляет «пропущено N записей» при сбросе.
Поток eg-log ждёт Condvar без таймера при пустом буфере. Первая запись
взводит секундный срок; заполнение буфера или warn/error требуют раннего сброса.
Warn/error ждут записи и sync_data; ошибки файлов доступны через `flush`.
При обычном завершении guard сбрасывает буфер и останавливает поток.

Хук Rust-паники сам синхронно пишет буфер, маскированное сообщение и принудительно
снятый бэктрейс (до 4096 байт), затем sync_data. Он не вызывает log и не ждёт
поток-писатель. Стандартный хук заменён, чтобы stderr не раскрыл секреты.
Крах в C/Skia, abort и убийство процесса системой не вызывают хук: ещё не
сброшенные info могут потеряться. Сбой диска также не позволяет гарантировать
сохранность warn/error. В stripped-релизе бэктрейс может содержать только адреса;
для символизации используйте profiling-сборку.

`eagle_core::Token` и `SignedUrl` маскируют Display/Debug; URL целиком скрыт, включая подписи в пути, query,
fragment и userinfo. Для сетевого запроса нужен явный `expose()`.
Сырые диагностические записи ureq отключены независимо от фильтра: они содержат
полные URL и HTTP-заголовки. Бэкенд без regex дополнительно маскирует token/sign/signature и другие
известные параметры, Authorization и Cookie. Это страховка: произвольный
секрет без метки распознать нельзя. На info разрешены provider и track_id,
запрещены названия треков и поисковые запросы. Логи должны подходить для
публичных issues. Оба уровня маскировки проверяются тестами.

Сравнение бэкендов воспроизводится командой
`python3 bench/compare_loggers.py --seconds 60`: изолированные release-пробы
пустого процесса, своего бэкенда и flexi_logger; зависимость flexi_logger
не добавляется в workspace. Решение и замеры — в [ADR](docs/adr/0001-logging.md).

## Аккаунты, секреты и логи

Использовать отдельные тестовые аккаунты Яндекса и VK. Основные аккаунты не
использовать для проверки неофициального клиента. Аккаунты создаёт владелец;
автоматического создания и подключения аккаунтов в каркасе нет.

Ключи и client_id передавать через окружение сборки или config.local.toml
(исключён из Git). Загрузчик конфигурации появится вместе с провайдерами.
Никогда не логировать токены, Authorization, query-параметры подписанных URL
и полные URL треков. До появления сетевого кода логирование этих данных запрещено.

## Публикация

Перед каждым первым push: `gitleaks detect --source . --log-opts="--all" --redact`.
Также проверьте текущие файлы: `gitleaks dir . --redact`.
CI запускается в GitHub Actions; локальные мобильные проверки требуют rustup,
целевых std, NDK/cargo-ndk для Android и полного Xcode для iOS.

Будущие рабочие потоки называйте `eg-*`, максимум 15 символов. Для ручной
сверки Linux можно использовать bpftrace (root) по sched:sched_wakeup;
непосредственные wakeup-события и voluntary switches не всегда взаимно однозначны.
